# Agent Note: Pwsh 启动以标记提示符为准

Status: implemented

[English](2026-09-17-pwsh-startup-marker-readiness.md) | 中文

## 问题

运行真实 pwsh 的每条 CI 平台都在启动时失败。Linux 的首次启动发送在启动阶段的读取上按精确 stdin 等待档结算，发布了只含设置命令回显的 motd；macOS 没有精确档，空的后续发送循环按 `inferred_idle` 反复结算直到绝对截止时间。Windows pwsh 在本地同样表现此竞态。回显证明这行命令到达了 tty，但 prompt 函数从未渲染标记：在 pwsh 交互循环启动之前提交的一行命令可能被 shell 自身的启动终端探测消费掉而不执行。上一个修复保留了最近非空视口，但仍在裸 `stdin_read` 上跳出启动循环，于是过早的结算发布了一个从未安装提示符的 shell。

## 决策

[启动流程](../../../../packages/terminal/terminal-bash/src/index.ts)现在把受控提示符标记作为 pwsh 启动完成的唯一证据：`LocalPtySession.promptAcknowledged` 报告自 spawn 以来观察到标记及其可打印的 `dsh> ` 尾部，启动循环只在该标志上跳出。没有标记的结算会重新提交这个幂等的设置；从第三次未确认结算起，先提交一个空行取消被部分消费的行再重新提交。确认标记之后，启动会等待输出流归于静默：排队的重提交会不断重新渲染标记提示符，终端自身对确认行的回显也可能作为滞后突发到达，因此立即开始的发送会按残留的启动输出而不是自己的命令结算。单一绝对截止时间限制整个循环与静默窗口，shell 退出或超时仍然拒绝打开。设置命令的回显一直包含可打印提示符，这正是证据来自清洗器的标记跟踪而非视口文本的原因。

Windows 专属真实 shell 用例现在按平台推导 `Set-Location /` 的落点，因为 Windows pwsh 解析到的是当前盘符根而不是 POSIX 根。

## 已考虑的替代方案

**放宽超时或盲目重试。** 拒绝：截止时间不是所等待的状态；没有标记证据时每次重试都以同样方式结算，循环只会耗尽截止时间。

**把默认 `PS` 提示符或回显的设置文本当作就绪。** 拒绝：打印的提示符证明渲染发生，不证明提交的输入会执行；回显源在 shell 就绪前就包含可打印提示符字面量。

**等到 shell 打印输出后再首次提交。** 拒绝：没有可观察信号能区分"提示符已打印"与"交互循环正在消费输入"，而重新提交无论 shell 何时就绪都会收敛。

## 后果

POSIX 启动在常见情形多付一次结算周期；退化路径每次尝试增加一次 `inferred_idle` 等待，仍在一个截止时间内。真实 shell 套件在 POSIX 上仍由 CI 负责；模拟启动测试固定了重提交与清空序列。本笔记取代[检查点顺序笔记](2026-09-16-checkpoint-order-and-terminal-startup.zh.md)的 pwsh 段落——该段在跨空结果保留输出的同时仍只要求 `stdin_read`；该笔记的其余决策不受影响。
