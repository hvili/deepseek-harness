# Agent Note: 工作区注记的客户端覆盖

Status: implemented

[English](2026-09-17-workspace-annotation-client-coverage.md) | 中文

## 问题

持久收藏/标签功能交付时只在客户端测试替身中加了假 API 管道，没有任何用例驱动新的客户端路径：模型的收藏/取消收藏/标签方法、follow 流增量 switch 的分支、控制器门面方法、UI 导航面、测试运行时的 workspaces 替身都从未被执行。Windows 覆盖率档——第一条真正跑到逐文件阈值检查的档——以十二个工作区文件共 384 个未覆盖位置失败。Linux 档之所以"通过"覆盖率门禁，只是因为 pwsh 启动失败让该档在阈值检查之前就中止了，所以缺口与平台无关、此前不可见。

## 决策

行为测试通过每层的真实入口覆盖各层。注册表套件驱动收藏、标签规范化、上限与重启持久性。控制器 host 套件驱动四个命令及其失败映射，以及 feed 的收藏/会话标签/工作区标签变更检测。客户端模型套件安装一元回显、保持失败结果不变，并证明结构相等的标签映射不触发发布。传输套件把三种新增量类型推过 Gateway 客户端，并把门面命令以线上请求驱动。UI 套件渲染收藏标记、标签片段与收藏菜单的两个方向，并派发标签编辑器；搜索推导匹配持久的 Workspace 与 Session 标签。测试运行时的 workspaces 替身有了自己的套件，覆盖默认镜像行为、stub 座位与调用记录。

## 已考虑的替代方案

**把十二个文件从逐文件门禁豁免。** 拒绝：门禁是仓库的覆盖契约，缺口是缺失的套件而不是收集工件。

**只通过浏览器级档位覆盖客户端路径。** 拒绝：jsdom 与 remote-mock 档已经执行了这些函数中的每一个；缺失的覆盖是未测试的功能面，不是测试设施限制。

## 后果

客户端注记面在每条平台档上都有行为固定，下一条跑到阈值检查的档不再决定什么算覆盖。收藏/标签的 UI 交互仍由功能提交中记录的浏览器演练做过视觉验证；这些套件固定的是其逻辑而非渲染。
